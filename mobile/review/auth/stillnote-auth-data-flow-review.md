# StillNote 인증 데이터 흐름 검토

작성일: 2026-10-31. 검토용이며 공개·신고용 확정 문서가 아니다.

## 결론

SDK 추가 버전에 기존의 ‘수집 없음’ 신고를 그대로 재사용하지 않는다. 현재 SDK 초기화에서의 처리와, 향후 사용자가 선택할 인증에서의 처리를 나누어 검증한다. 개인정보처리방침과 Play 응답 초안은 준비했지만 실제 배포·제출은 보류한다.

## 근거 범위

- 코드: PR #25, 커밋 `c9c6ebcff3842b731e48a0d0b6e8b709b68e4467`.
- 의존성: BoM 35.1.0, Auth 25.0.0, reCAPTCHA 18.6.1.
- 확인: APK SDK 속성 파일·AAR 매니페스트·POM·CI 릴리스 권한 검사. 컴파일 성공.

## 해석상 주의

Firebase 공식 안내는 Auth가 기본적으로 처리하는 기술 정보와, 개발자가 선택한 인증 방식에 따라 처리하는 이메일·UID 등을 구분한다. ‘로그인 선택 가능’이라는 이유로 SDK가 자동 처리하는 모든 정보를 선택 수집이라고 답하지 않는다. [Firebase 데이터 공개 안내](https://firebase.google.com/docs/android/play-data-disclosure#authentication)

reCAPTCHA 공식 자료는 SDK 요청 수신 시 IP·SDK/패키지·동작·기기 무결성·상호작용·일부 설치 앱·기기 식별자 등을 공개한다. 이는 우리 앱의 해당 버전이 전 항목을 실제 수집한다는 증거가 아니다. SDK 버전·구성·실행 조건별 확인이 필요하다. [reCAPTCHA 공개 안내](https://docs.cloud.google.com/recaptcha/docs/disclosure-requirements-android)

Firebase의 일반 안내상 Auth 서비스는 미국에서 처리되고, 인증 정보와 IP의 보관 방식이 다르다. 앱 계정 삭제·문의 보관 정책을 이 공급자 안내만으로 확정하지 않는다. [Firebase 개인정보 안내](https://firebase.google.com/support/privacy)

## 제출 전 해결할 항목

1. SDK 연결 APK의 신규 설치·첫 실행·오프라인 메모 사용에서 실제 통신과 수신처를 확인한다.
2. 인증 구현 후 회원가입·로그인·비밀번호 재설정·로그아웃·계정 삭제 경로를 확인한다. 실제 자격 증명과 토큰은 보고서·로그에 남기지 않는다.
3. SDK 기본 수집의 Play 유형·필수/선택·목적·공유 예외를 최종 판정한다.
4. 계정 생성 도입 시 앱 내 삭제 경로와 외부 웹 요청 경로를 구현·검증한다. 로컬 메모·백업·계정 데이터의 삭제 범위를 구분한다.
5. 최종 AAB에 맞춰 앱 내 정책·웹 정책·Play 응답을 일치시킨 뒤 공개한다.
